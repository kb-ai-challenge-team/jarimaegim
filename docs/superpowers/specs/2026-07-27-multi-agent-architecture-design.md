## 0. 확정 결정

| # | 결정 | 근거 |
|---|---|---|
| 1 | **실제 LLM 멀티에이전트를 도입한다** | 사용자 결정. v1.0 쟁점 1의 반전 |

| 4 | **권장 밴드로 자동 진행하고 확장·축소 배너를 대칭 제시한다** | 후보를 보기 전 금융 결정을 요구하지 않음 (이탈 방지 + 권유 편향 방지) |

- 초기 후보 생성 개수는 **8개**로 고정한다(원안의 8 vs 10 불일치를 8로 통일).
- 최종 후보 개수는 **고정하지 않는다.** 탈락 사유가 있는 것만 탈락한다.
- 스코프는 **서울 25개 자치구**로 유지한다(부록 A 불변조건 6).
- `mode` 필드와 `ModeProfile` 디스패치는 유지하되 구현체는 예비창업 1종이다(v1.0 쟁점 2 계승).

## 1. 시스템 경계

```
Layer 0  계약        models.py ↔ lib/types.ts (단일 진실 원천)
Layer 1  오케스트레이션  메인 에이전트 (LLM) — 팀 호출 순서는 코드가 고정, 팀 내부는 LLM
Layer 2  전문 에이전트   3팀 · 서브 9 (LLM + 도구)
Layer 3  도구          데이터 조회 어댑터 + 순수함수 계산기 (LLM 없음)
Layer 4  영속화        AnalysisRepository · 케이스 단위 결과 저장
Layer 5  게이트        EvidenceGate — 사용자에게 도달하기 전 마지막 관문
```

**팀 호출 순서는 LLM이 결정하지 않는다.** 조건 → 금융 → 입지 → 축소 → 타이밍 → 레포트 순서는 코드에 고정된다. LLM의 자유도는 **팀 내부에서 어떤 도구를 어떤 순서로 호출할지**에만 존재한다. 이것이 v1.0이 우려한 무한 재계획을 구조적으로 막으면서 멀티에이전트의 이점을 얻는 형태다.

## 2. 에이전트 레지스트리

12개 에이전트(메인 1 · 조건 2 · 서브 9)가 각각 다음 계약을 선언한다.

```python
class AgentSpec(BaseModel):
    key: str                        # "location.demand"
    team: Literal["MAIN","CONDITION","FINANCE","LOCATION","TIMING"]
    display_name: str
    data_sources: list[str]         # DataSourceSpec.key 참조
    evidence_grade: Literal["A","B","C","U"]
    tools: list[str]                # 허용 도구 화이트리스트
    enabled: bool                   # 원천 미검증 → False
    disabled_reason: str | None
```

| key | 팀 | 산출물 | 등급 | LLM |
|---|---|---|---|---|
| `main.orchestrator` | MAIN | 대화 요약 · 팀 보고 통합 · 문서 초안 | — | ✔ |
| `condition.location` | CONDITION | 업종 · 자치구 · 평수 · 운영형태 · 희망 임대조건 | — | ✔ (정규식 1차, 폴백만) |
| `condition.finance` | CONDITION | 자기자본 · 기존부채 · 월고정지출 · 신용상태 | — | ✘ |
| `finance.band` | FINANCE | **조달 밴드 3중선 + 손익분기선** | B | ✘ |
| `finance.kb_products` | FINANCE | KB 상품 조합 · 금리 · 월 상환 | B | ✘ |
| `finance.subsidy` | FINANCE | 지원사업 매칭 · 조달선 상향분 | B | ✘ |
| `finance.stress` | FINANCE | 매출 −20/−30%, 금리 +1%p 시 유지 여부 | B | ✘ |
| `location.demand` | LOCATION | 유동·상주·직장인구 · 배후 구매력 | B | ✘ |
| `location.competition` | LOCATION | 동종 점포밀도 · 개폐업 추세 | B | ✘ |
| `location.viability` | LOCATION | **목표매출 vs 상권 동종 추정매출 분포** | B | ✘ |
| `location.survival` | LOCATION | 18/24개월 영업유지율 | A | ✘ |
| `timing.policy` | TIMING | 계약 시점 권고 또는 판단 유보 | C/U | ✘ |

**12개 중 LLM을 쓰는 것은 2개다.** `main.orchestrator`와 `condition.location`(정규식 폴백 시). 나머지 10개는 도구 호출과 순수 계산이며, 팀장 계층은 서브 결과를 집계하는 Reducer로서 LLM 없이 동작한다.

> 멀티에이전트를 도입한다는 결정과 "모든 에이전트가 LLM"이라는 것은 별개다. 부록 A 불변조건 4를 지키려면 숫자를 만드는 에이전트는 LLM일 수 없다. 멀티에이전트 구조는 **역할·계약·부분실패 경계**로 실현되고, LLM은 그 구조를 조립·설명하는 지점에만 놓인다.

## 3. 데이터 요구 명세

이 절이 이 스펙의 핵심이다. **원천이 확보되지 않으면 해당 에이전트는 켜지지 않는다.**

### 3.1 원천 카탈로그

각 원천은 다음을 선언한다.

```python
class DataSourceSpec(BaseModel):
    key: str
    provider: str                   # 제공기관
    dataset_name: str               # 정식 데이터셋명
    required_fields: list[str]       # 없으면 기능이 성립하지 않는 필드
    spatial_unit: str
    update_cadence: str
    evidence_grade: Literal["A","B","C","U"]
    access: Literal["OPENAPI","FILE","MANUAL","NONE"]
    endpoint_env: str | None        # .env 변수명 — 검증 전에는 공백
    verified: bool                  # 실측 검증 통과 여부
```

#### DS-01 · 서울시 상권분석서비스 — 추정매출

| 항목 | 값 |
|---|---|
| 제공기관 | 서울특별시 (서울 열린데이터광장) |
| 데이터셋 | 서울시 상권분석서비스(추정매출-상권) |
| 필수 필드 | `상권_코드`, `상권_코드_명`, `서비스_업종_코드`, `서비스_업종_코드_명`, `당월_매출_금액`, `당월_매출_건수`, `점포수`, `기준_년분기_코드` |
| 선택 필드 | 요일별·시간대별·성별·연령대별 매출 금액 (수요 프로파일 정밀화용) |
| 공간 단위 | 상권 (골목/발달/전통시장/관광특구) |
| 갱신 | 분기 |
| 등급 | **B** |
| 접근 | OpenAPI + 파일 다운로드 |
| 상태 | **미검증** — 엔드포인트 계약 실측 필요 |

> **이 데이터셋이 `location.viability`의 유일한 근거다.** 목표매출(일 38만)을 이 분포에 대입해 백분위를 산출한다. `당월_매출_금액 ÷ 점포수`로 점포당 평균을 도출하되, **분포의 산포를 알 수 없다는 한계**를 provenance에 명시한다. 상위 10% 경계는 평균만으로는 계산할 수 없으므로, 분위 정보가 없으면 판정 기준을 "동종 평균 대비 비율"로 낮춘다(§3.7 참조).

#### DS-05 · 행정안전부 지방행정 인허가데이터 (LOCALDATA)

| 항목 | 값 |
|---|---|
| 제공기관 | 행정안전부 |

| 갱신 | 일 단위 변경분 + 전체분 |
| 등급 | **A** — 개별 점포 이력이므로 유일한 A등급 경로 |
| 접근 | OpenAPI + 파일 다운로드 |

> `location.survival`의 근거. 코호트 구성 방식: 특정 상권·업종에서 **기준 시점 이전에 인허가된 사업장** 중 18개월 후 `영업상태명`이 영업 중인 비율. 폐업일자가 있는 건은 생존기간을 계산해 카플란-마이어 없이도 단순 유지율을 산출할 수 있다. **폐업 신고 지연으로 유지율이 과대 추정되는 편향**을 provenance limitations에 명시한다.

#### DS-06 · 금융감독원 금융상품통합비교공시 (finlife)

| 항목 | 값 |
|---|---|
| 제공기관 | 금융감독원 |
| 데이터셋 | 정기예금 / 적금 / 주택담보대출 / 전세자금대출 / 개인신용대출 |
| 필수 필드 | `fin_prdt_cd`, `kor_co_nm`, `fin_prdt_nm`, `lend_rate_min`, `lend_rate_max`, `lend_rate_avg`, `rpay_type_nm`, `lend_rate_type_nm` |
| 등급 | B |
| 상태 | **배선 완료** (`OfficialSourceService`) |

> **중대한 갭.** finlife는 **소비자 대출만** 공시한다. **개인사업자 대출·창업자금 대출은 포함되지 않는다.** 따라서 `finance.kb_products`가 finlife만으로는 창업자금 상품을 제시할 수 없다. 대응은 §3.3(제도·상품 파라미터)이며, 그 전까지 이 에이전트는 **"창업자금 상품 정보 연동 대기"**를 반환하고 소비자 대출 상품만 참고 정보로 표시한다. 이 갭을 감추지 않는 것이 부록 A 불변조건 1의 이행이다.

### 3.3 API가 아닌 데이터 — 제도·상품 파라미터

조달 밴드를 계산하려면 공개 API로 얻을 수 없는 규정값이 필요하다. 이들은 **버전 관리되는 설정 파일**로 두고, 값의 출처와 기준일을 함께 기록한다. 코드에 상수로 박지 않는다.

| 파라미터 | 필요한 이유 | 출처 성격 | 담당 |
|---|---|---|---|
| 지역신용보증재단 보증한도·보증료율 | 최대 조달선 계산 | 재단 규정. 지자체별 상이 | 수기 등록 |
| 소상공인 정책자금 한도(일반경영안정자금 등) | 조달선 상향분 | 소진공 공고 | 수기 등록 |
| 신용보증기금 보증 조건 | 최대 조달선 | 기금 규정 | 수기 등록 |
| KB 창업자금·개인사업자 대출 상품 조건 | `finance.kb_products` 갭 해소 | **KB 내부 상품 정보** | 사업부서 제공 필요 |
| 업종별 표준 초기투자 항목·비율 | 필요자금 산정 보조 | 소진공 창업 가이드 등 | 수기 등록 |
| 업종별 표준 원가율·인건비율 | 손익분기 매출 산출 | 통계청 서비스업조사 등 | 수기 등록 |

> **`finance.kb_products`의 실질적 해소 경로는 API가 아니라 KB 내부 상품 정보다.** 이 스펙은 그것이 제공되지 않은 상태에서도 시스템이 거짓말하지 않도록 설계되어 있다.

| 인테리어·설비 예상비 | 업종·평수별 편차가 큼 | 업종 표준 비율(§3.3)을 **초기값으로 제시하고 사용자가 수정** |

### 3.5 구현 함정 — 세 개의 매핑

이 세 가지가 데이터 확보보다 더 많은 시간을 쓰게 될 지점이다.

**(1) 좌표계 변환.** Kakao Local은 WGS84(EPSG:4326)를 반환한다. 서울 상권분석 영역-상권의 `엑스좌표_값`/`와이좌표_값`과 LOCALDATA의 `좌표정보(x/y)`는 **TM 계열 투영좌표**이며, 정확한 EPSG는 데이터셋별로 다를 수 있다(5174/5179/5181 계열). **각 원천의 EPSG를 실측으로 확정한 뒤 `pyproj`로 변환한다.** 확정 방법: 알려진 지점(예: 서울시청)의 좌표를 각 원천에서 찾아 변환 결과를 대조한다. **EPSG를 추측으로 정하면 후보가 수백 미터 어긋나고, 그 오차는 화면에 오류로 나타나지 않는다.**

**(2) 업종 코드 4-way 매핑.** 다음 네 체계를 연결해야 한다.

```
사용자 자유 입력 ("카페", "커피숍", "브런치 카페")
    ↓
서울 상권분석 서비스_업종_코드 (CS 계열)      → DS-01/02
    ↓
LOCALDATA 개방서비스명 + 업태구분명           → DS-05
    ↓
(참조) 통계청 표준산업분류 KSIC
```

매핑 테이블은 **검증 자산**으로 관리하고, 매핑에 실패한 업종은 해당 축을 비활성화한다. 임의로 가까운 코드에 붙이지 않는다. **잘못된 매핑은 조용히 틀린 생존율을 만들며, 이것이 이 설계의 최대 위험(§11-2)이다.**

**(3) 상권 경계 매칭.** 서울 상권분석은 상권 폴리곤 내부만 커버한다. 후보 좌표가 어떤 상권에도 속하지 않으면 DS-01~03을 조회할 수 없다.

> **대응: 후보를 상권 폴리곤 내부에서 생성한다.** Kakao Local로 자유 검색한 뒤 상권을 찾는 순서가 아니라, **밴드 내 상권을 먼저 고르고 그 안에서 후보를 뽑는다.** 이 순서가 §5 흐름에 반영되어 있다. 폴리곤 밖 후보는 "상권 데이터 범위 밖"으로 표기하고 4축을 판정하지 않는다.

### 3.6 확보 순서와 각 단계가 여는 기능

각 단계는 독립적으로 출하 가능하며, 이전 단계 없이는 다음 단계가 의미를 갖지 않는다.

| 단계 | 확보 대상 | 여는 것 | 완료 정의 |
|---|---|---|---|
| **D0** | 외부 API 없음. **§3.3 제도 파라미터 수기 등록**만 필요 | 조달 밴드 3중선 · 손익분기선 · 스트레스 테스트 | 자기자본·임대조건을 바꾸면 3중선과 목표매출이 바뀐다. 지원금·상품 정보는 "연동 대기"로 표시된다 |
| **D1** | DS-04 영역 + 좌표계 확정 | 후보 ↔ 상권 매핑. 이후 모든 입지 축의 전제 | 임의 후보 좌표에서 상권 코드가 결정론적으로 나오고, 폴리곤 밖은 명시적으로 구분된다 |
| **D2** | DS-01 매출 + 업종 매핑 | **`location.viability`** — 되먹임 반전의 핵심 | 목표매출의 상권 내 위치가 B등급으로 산출되고, 분위 정보 부재 시 판정 기준이 자동 하향된다 |
| **D3** | DS-02 점포 + DS-03 인구 | `location.competition` · `location.demand` | 후보별 수요·경쟁 등급이 나오고 축별 실패가 격리된다 |
| **D4** | DS-07/08 지원사업 | `finance.subsidy` — 조달선 상향분이 후보 수를 바꾼다 | 지원금 매칭 시 권장 조달선과 열리는 상권 수가 함께 변한다 |
| **D5** | DS-09 임대 수준 | **밴드별 상권 스크리닝** — "1억이면 3곳, 1.45억이면 11곳" | 배너의 상권 개수가 실제 데이터로 채워진다. 실패 시 §3.7 대체 경로 |
| **D6** | DS-05 인허가 + 코호트 구축 | `location.survival` — **유일한 A등급** | 상권·업종별 18/24개월 유지율이 표본수와 함께 산출되고, 매핑 실패 업종은 비활성화된다 |
| **D7** | DS-10 일정 | `timing.policy` 실동작 | 착수 조건: 정형 원천 확보. **미확보 시 착수하지 않고 판단 유보를 유지한다** |

**D0은 외부 데이터 없이 출하 가능하며, 제품의 핵심 주장(조달 밴드)을 이미 담고 있다.** D1→D2가 되먹임 반전을 완성하고, D5가 가장 강한 문장을 만든다. D6가 등급 천장을 A로 올린다.

> **구현 계획의 범위.** 이 스펙은 D0~D7의 8단계를 담고 있어 단일 구현 계획으로는 너무 크다. **첫 구현 계획은 D0으로만 범위를 한정한다.** D1 이후는 각 단계의 원천 검증 결과에 따라 별도 계획으로 분리한다. D5·D7은 원천 확보가 선행 조건이므로 계획 수립 자체를 보류한다.

### 3.7 미확보 시 동작 계약

부록 A 불변조건 1의 구체적 이행. **모든 미확보 상태에 대해 반환값이 사전에 정의되어 있어야 한다.**

| 미확보 항목 | 반환 | 화면 문구 | 탈락 판정에 사용 |
|---|---|---|---|
| DS-01 (매출) | `StepResult(status="integration_pending")` | "목표매출 달성 가능성은 상권 매출 데이터 연동 후 판정됩니다" | **불가** |

**공통 규칙 두 개.**

1. **가동 불가 축은 어떤 경우에도 탈락 근거로 쓰지 않는다.** 판정하지 않은 것과 판정해서 통과시킨 것은 다르며, 둘을 구분하지 않으면 축이 늘어날수록 탈락이 자동으로 늘어난다.
2. **`GET /api/v1/status`에 축별 가동 여부를 노출하고 화면에 "N개 축 중 M개 가동"을 표시한다.** 감추지 않는 것이 서사 자산이다.

```
POLICY_PARAMS_PATH=config/policy-params.json
```

기존 `SEOUL_COMMERCIAL_API_URL`은 데이터셋이 다섯 종으로 분리되므로 위 변수들로 대체하고 제거한다.

## 4. 데이터 모델

`backend/app/models.py`와 `lib/types.ts`에 필드 단위로 동시 반영한다(단일 진실 원천 유지).

### 4.1 신규

```python
class FundingBand(StrEnum):
    EQUITY_ONLY = "EQUITY_ONLY"        # ● 자기자본선
    RECOMMENDED = "RECOMMENDED"        # ◐ 권장 조달선 — 스트레스 통과 최대
    MAXIMUM     = "MAXIMUM"            # ◑ 최대 조달선 — 추정치
    OUT_OF_RANGE = "OUT_OF_RANGE"      # ○ 조달 불가

class BandLine(BaseModel):
    band: FundingBand
    ceiling_krw: int
    monthly_repayment_krw: int
    runway_months: int                  # 현금소진 시점
    stress_pass: bool
    subsidy_uplift_krw: int = 0         # 지원금 반영 상향분
    is_estimate: bool                   # MAXIMUM은 항상 True
    trade_area_count: int | None = None # DS-09 미확보 시 None
    provenance: Provenance

class BreakEven(BaseModel):
    monthly_fixed_cost_krw: int
    target_monthly_revenue_krw: int
    target_daily_revenue_krw: int
    assumptions: list[str]              # 원가율·인건비율의 출처와 기준일
    provenance: Provenance

class AxisVerdict(BaseModel):
    axis: Literal["DEMAND","COMPETITION","VIABILITY","SURVIVAL"]
    status: Literal["JUDGED","INTEGRATION_PENDING","OUT_OF_RANGE","MAPPING_FAILED"]
    grade: Literal["A","B","C","U"] | None
    band: Literal["FAVORABLE","NEUTRAL","CAUTION"] | None
    metric_label: str | None            # "동종 평균 대비 118%"
    sample_n: int | None
    reason: str | None                  # status != JUDGED 일 때 필수
    provenance: Provenance | None

class Elimination(BaseModel):
    rule: Literal["BREAKEVEN_UNREACHABLE","STRESS_FAILED","OUT_OF_FUNDING_RANGE"]
    reason_text: str                    # 사용자에게 보이는 사유
    evidence_ids: list[str]             # EvidenceGate 추적용

class CandidateVerdict(BaseModel):
    candidate: Candidate
    band: FundingBand
    axes: list[AxisVerdict]
    eliminated: Elimination | None       # None이면 잔존
    soft_flags: list[str]                # 탈락 아님. "18개월 유지율 업종 평균 이하"
```

### 4.2 불변조건 강제

`BandLine`과 `CandidateVerdict`에 다음 `model_validator`를 둔다.

1. `band == MAXIMUM` → `is_estimate is True` 강제.
2. `AxisVerdict.status != "JUDGED"` → `grade is None and band is None` 강제. **판정하지 않은 축이 등급을 가질 수 없다.**
3. `Elimination.rule`이 참조하는 축이 `JUDGED`가 아니면 검증 실패. **가동 불가 축으로 탈락시키는 것을 타입 레벨에서 금지한다.**
4. `axis == "SURVIVAL"`이고 `grade != "A"` → 유지율 수치 필드를 허용하지 않음(부록 A 불변조건 2).

`lib/types.ts`에는 동일 구조를 판별 유니온으로 두고 `switch`를 `assertNever`로 닫는다.

## 5. 실행 흐름과 상태

```
조건 확정
  condition.location  → 입지 조건
  condition.finance   → 금융 프로필
  최소 조건 체크리스트 미충족 → 질문 ≤3개 (답이 후보를 바꾸는 항목만)
        ↓
[얼마] FINANCE — 후보 무관 1회
  finance.band / finance.subsidy / finance.kb_products / finance.stress
  → BandLine × 3 + BreakEven
        ↓
◐ RECOMMENDED 밴드 자동 선택 (사용자에게 묻지 않음)
        ↓
후보 생성 — 밴드 내 상권을 먼저 고르고 그 안에서 8개 (§3.5-3)
        ↓
[어디] LOCATION — 후보별 4축
  location.demand / competition / viability / survival
  → CandidateVerdict × 8
        ↓
축소 (§6)
        ↓
[언제] TIMING — 잔존 후보만. 미확보 시 ABSTAIN
        ↓
확장·축소 배너 → 클릭 시 **입지팀만 재실행** (BandLine 3종은 이미 산출됨)
        ↓
사용자 최종 1개 선택 → 자금조달 레포트(재계산 없음) → 문서 초안 → (선택) 상담 첨부
```

### 상태

v1.0의 6종을 유지하고 의미만 확장한다.

| 상태 | 의미 |
|---|---|
| `COLLECTING` | 최소 조건 미충족 |
| `RUNNING` | 파이프라인 진행 중. 팀·에이전트 단위 진행률을 `StepResult`로 관측 |
| `READY` | 잔존 후보 ≥ 1 |
| `NEEDS_INPUT` | 질문 대기 |
| `INSUFFICIENT_DATA` | **잔존 후보 0 또는 `finance.band` 실패.** `evidence_grade="U"`와 1:1 |

`finance.band` 실패는 후속 전체 중단이다. 기준선 없이는 후보를 판정할 수 없다.

## 6. 축소 규칙

```
하드 탈락 — 사유와 근거 ID가 있어야만 성립
  BREAKEVEN_UNREACHABLE   목표매출이 상권 동종 분포 상위 경계 초과
                          (분위 부재 시 → 동종 평균 대비 임계 비율, 기준 명시)
  STRESS_FAILED           매출 −20% 시 6개월 내 현금 소진
  OUT_OF_FUNDING_RANGE    필요자금 > 최대 조달선

소프트 표시 — 탈락 아님, 조건부로 잔존
  18/24개월 유지율이 업종 평균 이하
  경쟁 밀도 상위 + 신규 개업 증가 추세
  타이밍 판단 유보

금지
  가동 불가·판정 불가 축을 근거로 한 탈락 (§4.2-3에서 타입 강제)
  개수를 맞추기 위한 탈락
```

**최종 개수는 고정하지 않는다.** 8개가 다 남을 수도, 1개만 남을 수도 있다. 탈락 목록과 사유는 접힌 상태로 항상 함께 제시하며, 이것이 조건 변경 재계산의 진입점이 된다.

## 7. LLM 경계와 가드 3종

멀티에이전트를 도입하면 v1.0의 결정론이 제공했던 재현성이 사라진다. 다음 셋이 그 대체물이며, **셋 중 하나라도 없으면 이 아키텍처는 금융 도메인에서 방어할 수 없다.**

### 가드 1 — 숫자는 도구 결과만

에이전트별 도구 화이트리스트(`AgentSpec.tools`)를 두고, LLM 출력의 모든 수치는 도구 반환값에 대응해야 한다. 구현: 도구 반환값을 `evidence_id`가 붙은 사실 목록으로 축적하고, LLM 응답에 `[E1]` 형식 마커를 요구한 뒤 **숫자를 포함하면서 마커가 없는 문장을 후처리로 제거**한다(v1.0 `EvidenceGate` 계승). 결정론적이고 단위 테스트 가능하며 추가 LLM 호출이 0회다.

이것이 부록 A 불변조건 4의 이행 방식이다. **LLM이 도구를 고를 자유는 있고, 숫자를 만들 자유는 없다.**

### 가드 2 — 영속화, 동일 조건 재실행 금지

`AnalysisRepository`가 조건 해시별로 결과를 저장한다. 동일 조건 재조회는 저장된 결과를 반환하며 LLM을 호출하지 않는다. 재실행은 조건 변경 시에만 발생한다. 이것으로 사용자가 관측하는 비일관성이 제거된다.

부수 효과: `_candidate_index`의 프로세스 메모리 의존과 `GET /analyses/{id}` 404 스텁이 함께 해소된다(v1.0 §3 계승).

### 가드 3 — 원천 미검증 에이전트는 기본 비활성

`AgentSpec.enabled`의 기본값은 `False`이며, 원천 실측 검증을 통과한 경우에만 `True`가 된다. 비활성 에이전트는 §3.7의 반환값을 낸다. 검증 상태는 `GET /api/v1/status`에 노출된다.

### 모델

`LLMProvider` 추상화 뒤에 Claude Sonnet 5(`claude-sonnet-5`)를 둔다(v1.0 쟁점 7 계승). 키 부재 시 저하 경로는 현행 동작을 계승하며 대체 답변을 지어내지 않는다.

## 11. 위험

1. **DS-09(상권 임대 수준) 확보 실패가 가장 개연성 높다.** 실패 시 "1억이면 3곳, 1.45억이면 11곳"이라는 제품의 가장 강한 문장을 잃는다. 밴드 자체는 월 상환·소진 시점 비교로 유효하므로 제품이 무너지지는 않지만, 차별점이 약해진다. **추정값으로 메우지 않는다.**
2. **업종 코드 매핑 오류가 가장 위험하다.** 조용히 틀린 생존율을 만들고 화면에 오류가 나타나지 않는다. 매핑을 검증 자산으로 관리하고 실패 업종을 비활성화하는 것 외에 방어 수단이 없다.
3. **DS-01의 분위 정보 부재.** 평균만으로는 "상위 10% 경계"를 계산할 수 없다. 판정 기준 하향(§3.7)이 준비되어 있으나, 이 경우 탈락 판정의 설득력이 낮아진다.
4. **`finance.kb_products`의 창업자금 갭은 API로 해소되지 않는다.** KB 내부 상품 정보 제공이 전제이며, 이는 기술 과제가 아니라 협업 과제다.
5. **밴드 제시의 권유 편향.** 확장·축소 대칭 노출로 완화하되 완전히 해소되지 않는다. 최대 조달선을 추정치로만 표기하는 것이 최소 방어선이다.
6. **추정매출의 카드 기반 편향.** 현금 비중 높은 업종에서 과소 추정되어 판정이 비관적으로 나온다. 낙관 방향 오류보다 안전하므로 감수하되 명시한다.
7. **LLM 멀티에이전트의 지연.** 약 15회 호출로 20~40초다. 가드 2가 재조회 지연을 제거하지만 최초 실행은 느리다. 팀·에이전트 단위 진행 표시가 필수다.
8. **가드 1의 문장 제거는 무딘 방식이다.** 숫자 포함 여부로 판정하므로 정당한 문장이 제거될 수 있다. 반대 방향 오류보다 안전하므로 의도적으로 감수하되 제거율을 로깅해 임계치를 조정한다.
9. **팀 호출 순서를 코드로 고정한 것은 되돌리기 쉽지 않다.** 도구가 늘어 조건부 분기가 실제로 생기면 병목이 된다. 전환 지점을 **도구 15종 초과**로 사전 정의한다.

이 스펙의 핵심은 아키텍처가 아니라 **§3.7 미확보 시 동작 계약**이다. 12개 에이전트 중 지금 정직하게 작동하는 것은 5.5개이고, 나머지 6.5개를 켜는 조건과 켜지지 않았을 때의 반환값이 전부 사전에 정의되어 있다. **구조를 다 만들어도 거짓말하지 않는 것**이 이 설계가 방어하려는 지점이다.
